## Findings
- **Verified (decompile SyncClient 0x100afab0 / 0x100b15d0)**: the soldier NAME in the row comes from DataSet[0x3e] (id -> name lookup, stored at row+0x78). We sent 112011 (V21 hard-code) so the row showed 屯駐矛兵. Cause of "lobby 3-star vs battle 1-star": battle_server hard-coded 112011 (Lv2 = stage 1) and never read last_prebattle.json armyid (which also held a stale 510009).
- AddPlayer message layout (struct offsets, SyncClient deserializer 0x10061820): +4 first uvar (`a`, we send the army id; no reader found in the AddPlayer path), +8 isSelf, +9 ptype, +0xd name, +0x25/+0x29 two uvars = id lookups into row strings +0x38/+0x58, +0x2d sname, +0x45 -> row+0xdc, +0x49 -> a separate map[uid], +0x4d/+0x51 unused here, +0x69 DataSet. DataSet[0x10] -> row team (+0xb4... ), DS[0x44] -> row+0xb8 (a counter that the stat code increments, so a stat, NOT a troop count), DS[0x49] -> row+0xf0, DS[0x4a] unread in AddPlayer.
- **Hypothesis**: the scoreboard total "112011" is one of the numeric slots we filled with 112011: first uvar `a`, or DS[0x44]/[0x49]/[0x4a]/[0x3f]/[0x43]/[0x47]. The current/total pair is read by the native GetPlayerSoldierNum(uid, out cur, out total) (Win32 exec 0xd69500 -> virtual +0x7f4 of KingdomSyncPlayerController; implementation NOT located, no RTTI). Troop counts probably also arrive via Cmd 0x4f1e MsgCmdMaxSupplyArmyNUM (layout never decoded) and the soldier add flow. A current count of 0 plausibly explains no troops; not proven.
- **Hypothesis**: enemy "?" is deliberate hiding of the other camp's stats (a=112011 and the same slots were sent for the enemy and it still shows "?"), so it is not by itself a bug. The enemy row proves the enemy PlayerCtl was created; no visible pawn is unexplained (possible causes: pawn spawn needs DS[0x26]/[0x27] speed slots like the hero (missing in V49/V51), or position/ReBorn timing).
