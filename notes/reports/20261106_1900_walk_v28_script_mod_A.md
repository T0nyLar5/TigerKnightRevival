## 1. Decoded move bursts (tools\battle_moves.py; verified)
- Axis convention (verified from data): **y = vertical**. Jump = 0x2738 mode 1 vel (0,+6,0) then mode 2 vel y falling 6 -> -6 (gravity ~10.5/s per 100 msgs), 0x2737 position y 3.1..5.8 within the burst. x = forward-ish, z = side; 2721 = velocity f16 (equals 2738 mode 2), 2737 = position f32.
- Bursts at 20, 24, 27 s: pure vertical (x,z velocity exactly 0; pos x constant 1.0, z 0) = plain jumps.
- Bursts at 30-31 s and 34 s (jump + move): horizontal velocity appears but is tiny: 30 s x 0.11 -> 0.49, z -0.09 -> -0.38; 31 s x -> 0.74, z -> -0.58; 34 s x -0.94 -> -0.14. Pos x 1.0 -> 1.47 over ~2 s. Roughly 0.4-0.5 units/s^2 acceleration, in the air only. Jump height ~2.7 units, so units are ~metres; a walk speed of 4.5 (NormalRunSpeed 450 uu) would be 10x larger and sent on the ground.
- Pre-mod logs show the SAME signature: 20261105_231519 (t=13 s: x 0.02 -> 0.46, z -0.73), 20261106_175712 and _180128 (x 0.13 -> 0.86). So mod A changed nothing measurable: the horizontal air drift existed before, so it is not caused by the PlayerInput zeroing block.
- Ground W / A / D (11-19 s): no message at all. The client reports 0x2738 / 0x2721 only while the pawn has non-zero velocity (jump). So on the ground the pawn's Velocity stays 0 = Acceleration (or GroundSpeed) is 0 or tiny, not an input-to-server problem.

## 3. Conclusion
- The script gates (aForward zeroing, input ignore, MatchHasBegun) are all ruled out by mod A + V28 (verified in effect: no change).
