# Pull-back after V37 walk + server echo variants V38/V39 (2026-11-07 22:00)
Log: server\logs\battleserver_20261107_214643.log (V37). Static: Win32 Ghidra copy tools\ghidra_projects_e (SyncClient/Sync/Kingdom-Win32). Win32 layouts are a proxy for the Win64 game (hypothesis unless marked).

## 1. What the client sends while walking (VERIFIED from the log)
- Per 50 ms (about 19-20/s each): 0x2737 ReqPosition (uid, f32 x,y,z metres, y = up) and 0x2721 ReqMove (uid, f16 x,y,z). Plus 0x2754 CamTurn ~8/s, 0x2738/0x2739 MoveStart/End on each W press/release, 0x2722 (208,99) on each End.
- 0x2721 is NOT a position: y is always 0.0 and x,z swing +-4 with sign flips (velocity/input-like). 0x2737 is the real position: starts (0.9, 4.17, -0.7), walking speed 2-4.5 m/s, y 4.0-4.2 (ground).
- Our server sends nothing back except empty frames and the countdown/BattleStart. No Cmd for the hero position at all.
- Sprint (double W): 0x273e (uid only) twice at t=14.2 s and 15.0 s, 0x2778 (uid + uvar `b9 df cd 08`) twice at t=13.3 s, 13.6 s. No reply -> nothing happens (hypothesis: the sprint start is a Req the server must confirm).

## 3. Mechanism (static; hypothesis, medium confidence)
- Kingdom-Win32 SmoothLocation FUN_00e726c0 (script native on KingdomSyncPawn): target = *(DAT_01717060+0x1c); if dist^2 <= DAT_0142e1f8 it lerps toward the target, else it TELEPORTS to the target (matches: hard jump at ~10 m = threshold squared 1e6 uu^2 (hypothesis, constant not read)).
- DAT_01717060 = per-local-hero struct (FUN_00df1e70, created in the local spawn FUN_00df26b0). +0x10..+0x18 = sync-side hero position, +0x1c..+0x24 = its collision-resolved copy (FUN_00de66e0 per tick copies +0x10 -> +0x1c, nudges by overlapping actors, MoveActor the pawn to +0x1c). Keys C/D saw these copies stuck at the spawn (1,0,5.07) m, exactly where the hero is teleported back to.
- The ONLY writer of +0x10 found: FUN_00db5ef0(this, x, y, z) (a KingdomPawn vtable method, 13 vtable refs, called from native; range check on x,y,z, pawn+0x394==0). It sets +0x10 and recomputes +0x1c. So the stuck value = nobody calls db5ef0 with the hero's moving position.
- SyncClient (Win32) 0x100a4370: handler for Cmd 0x4eca (CmdGhostPosition: uid, 3 x f16 = factory 0x1007d5b0) calls `sink->vtable[+0x40](&msg.pos)` with only the vec3 (uid dropped); 0x4ecb calls vtable[+0x44]. The sink is a Kingdom-side callback object -> very likely ends in a pawn position setter such as db5ef0 (NOT proven; sink class not identified).
- Client-side senders: ReqMove 0x2721 = SyncClient 0x100160e0 (compares its vec3 argument with unit+0x2c, sends if different), ReqPosition 0x2737 = 0x10016480. Neither updates the unit locally.

## 4. Why V23 broke jumping (best explanation, hypothesis)
V23 relayed 0x2721 body as Cmd 0x4eca. 0x2721 holds a velocity-like vec with y = 0 -> if 0x4eca sets the position, the hero is forced to (x, 0, z) = 4 m below the ground at the start -> cannot walk/jump. Also 0x2738/0x2739 were echoed as 0x4e50/0x4e51 (move-action Cmds the pawn applies). V34 (ghost stream) was sent while the hero could not walk and changed nothing visible; the stream also started from (9.3,..) not the real start (0.9,-0.7), so it is not evidence against 0x4eca.
