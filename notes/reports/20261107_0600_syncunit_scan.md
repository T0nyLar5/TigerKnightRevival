# Sync-unit memory scan (11-07 06:00): key C added, NOT run in game
Goal: find the vec3 that native SmoothLocation pulls the hero toward (hyp.: sync unit, Win32 *(DAT_01717060+0x1c)) by memory scan, then drive it. Win64 addresses unknown, so scan instead of Ghidra.

## What key C does (`英雄速度檢查.bat` C = `tools\ue_inspect.py --syncscan`, needs admin; numpy installed into tools\.venv)
1. Scan all committed private RW memory (pawn_probe.regions) for 3-number copies of hero Location: f32 and f64 in UU and in metres (/100), int32 fixed-point metres x1000/x10000/x65536; two axis orders (xyz and x,up,y = sync y-up); tol 0.5 UU; pawn object (hero..+0x4000) excluded; max 60 per type; prints first 30 (address, type, value).
2. Narrowing (up to 2 rounds): user holds W + jumps 6 s; candidates kept if they equal the hero's new position ("follows hero") or still the old one ("stays fixed"); others dropped.
3. Drive 10 s every ~10 ms: mode 1 candidate x += 3 UU per tick; mode 2 candidate = hero Location + Velocity*0.01. User may pick candidate ids. Prints hero Location each second, start->end x/y change, and per candidate how often the game overwrote our value (many = game updates it every frame = the real sync position).
Log saved to server\logs\pawn_probe_last.txt.

## Reading results
- Hero x/y changes a lot while driving -> pull target found; the candidate with high overwrite count is the live sync position; next find the writer / which message feeds it.
- No candidates at all -> sync position stored in another format (e.g. offset from origin, f16) or the scan hit nothing; try different axis/scale.
- Candidates but hero unchanged and overwrite counts 0 -> copies are stale/unrelated (e.g. controller or UI copies).
