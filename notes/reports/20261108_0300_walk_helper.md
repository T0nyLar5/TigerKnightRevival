Pointer changes (respawn, new battle in same process) are followed automatically; pawn/obj 0 -> prints "hero gone", polls at 200 ms. Checks the game is alive every 10 s status line and every 50 failed passes; exits when the game exits. Output: one status line per ~10 s. Assumption (hypothesis): Location offset stays valid for a new pawn (same class).

## 2. Who calls the setter (bounded investigation)
- Setter FUN_140aaf020 is in vtable slots at byte offset +0xaf8 (most pawn vtables, 9 of 13 hits) or +0xb10 in others; the vtable start detection is unreliable for adjacent vtables (offset 0xb10 hits in 0x1414aaeb8/0x1414ac358/0x1414e6f58/0x1414e8a28 are probably off by a neighbouring class), so trust 0xaf8.
- Raw byte scan for `call [reg+0xaf8]`: only 2 sites, 0x140a51ac7 and 0x140a572cf. `call [reg+0xb10]`: 4 sites (0x140a51e7f, 0x140a576e6, 0x140b054e2, 0x140b0676b); 0xb10 callers pass 7-8 args (different method), so not the setter.
- **0x140a51ac7 is in FUN_140a51a50 = native exec thunk `AKingdomPawn::execForceUpdatePlayerHumanLocation` (verified from the native table entry at 0x1417dbdf8 with the name string; declared in tools\work\cls\KingdomPawn.class.txt:4179 as `native function ForceUpdatePlayerHumanLocation(Vector NewLoc)`).** The thunk reads one Vector from UScript bytecode and calls vtable+0xaf8(this, &vec) = the setter. (verified statically; 0x140a572cf not decompiled, probably the sibling thunk.)
- So the ONLY route to obj+0x14 is a UnrealScript call `ForceUpdatePlayerHumanLocation(loc)` on the KingdomPawn. No server message calls it directly; if anything, a script function (reaction to a sync/server event, e.g. a teleport or a "player human position" event) calls it. Nobody calls it in our flow, hence obj+0x14 stays at spawn.
- NOT done: finding the UScript caller (bytecode in KingdomGame.u; FinalFunction tokens reference export index, not name, so a plain name grep does not work; name index in tools\work\KingdomGame_names.txt line 8043).
- No V45: no server message is identified. Variants 38-42 already tried relays without effect, consistent with this.
