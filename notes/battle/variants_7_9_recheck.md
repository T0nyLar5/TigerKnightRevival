## 2. Variant 5/6 re-check (SyncClient `0x100afab0` AddPlayer, `0x100b00b0`/`0x100ee480`/`0x100b4ec0` ReBorn, deserializers `0x10061820`, ctor `0x100cbf10`, Kingdom spawns `0x00e19260` remote / `0x00df26b0` local)
**Problems found in the shipped variants 5/6 (left unchanged, fixed in 7):**
1. **DataSet is far too small.** The UE3 spawn code reads DataSet indices {2,3,0x10,0x18-0x1b,0x1e-0x24,0x4b,0x4c,0x4e-0x57,**0x7e**} (tool `tools/dsget.py`; `0x7e` = 126). We send N=80. The Ctl keeps an exact copy of N words (`PlayerCtl` ctor `0x100cbf10`: `DataSet::vftable`, [4]=N, [5]=malloc(N*4)+memcpy), and the SyncClient code indexes it directly (`puVar6[0x44]`, ReBorn `piVar7[5]+0x24`). Reads >= N are heap over-reads (garbage, maybe a crash; whether the getter bounds-checks is not verified) [M]. Use **N >= 127**. Upper bound: the client re-serializes AddPlayer/ReBorn into a 0x400-byte stream buffer (`0x100afab0`, `0x100b00b0`), so keep 4*N + ~60 < 1024 -> N=132 used [M].
2. **DataSet[2] is HEALTH, not just "alive"**. Kingdom log string `+Remote Player team %d, health %d, weapon %d %d %d %d,helmetID %d,shawlID %d,armorID %d,shoesID %d,faceLen:%d` (arg order recovered from the pushes at 0xe19687..0xe196a9) gives: [0x10]=team, [2]=health (0 = "Remote Player Has Dead", no PlayerCtl), [0x18..0x1b]=helmet/shawl/armor/shoes ids (armor.txt), [0x1e..0x21]=weapon1..4 ids (meleeweapon/rangedweapon.txt), [0x22]=horse, [3]=second health-like value (max?), [0x4b], [0x4e..0x55] (8 values; armytype skilltype1-8? L), [0x4c],[0x56],[0x57] local player extras (flag id / hair style, log `+LocalPlayer ... flagID %d ... HairStyle %d`), [0x7e]==1 -> a bool passed to the spawn script event (L). Our variants had [2]=1 (alive) -> a 1-HP hero, zero gear.
3. **Position/direction live in the DataSet too** (ReBorn dispatcher `0x100b4ec0`: `iVar8 = ctl[5]` = DataSet: pos = (DS[9], DS[10], 0), dir = (DS[5], DS[6], DS[7]), DS[8]; floats as raw u32; `DS[0x4d] != 0` selects the mounted spawn callback (+0x48) instead of foot (+4); DS[0x33] must be < 5 else "Group Change Command Error"). Zero = origin facing +x. We keep zeros (map 17 nav is densest near the origin: (-2.7, 4.2, 2.3)). [M, the float interpretation follows the `float*` parameter of 0x00e19260]
4. Ordering: ReBorn itself does NOT need the slave unit (the data it reads is its own DataSet copy), so the timing worry for variant 5 (ReBorn sent before the slave frames) is probably harmless. What does matter: Sync.dll `0x10038440` (slave AddPlayer) looks the IPlayerEvent up by uid, so the top-level `0x4e22` must come BEFORE the slave AddPlayer (variants 5/6 do this) [H].
5. Slave `kind` = agentType: Sync.dll `0x10021430` (called with unit class 0 player / `a` person / 3 bullet, key kind) reports "can't find agentType(%d)" and passes a NULL config (-> `0x100658a0` memcpy from NULL = crash) when the key is not in `agentparam.txt`. kind=0 (player) is valid; the old `a=3`/kind=0 advice for soldiers was wrong: **soldier kind=1, a=1** (key semantics M; 0,1,2,4,5 exist, 3 does not).
6. Countdown (Kingdom `0x00ebfb00`, H): state 1 = prepare (script events with param 1 = freeze + timer UI `0xe6e1e0`), state 2 = tick (value = seconds left, stores `GameEngine[0x48e]=value`, clears flag 0x20000; **value 0 -> fires the "unfreeze" script events (names 0x170bb90/88) with param 0, sets flag 0x20000, calls vtable+0x6c4**), state 3 after 2 = running (sets flag 0x20000). Old sequence (1,3)(2,3)(3,0) never reached (2,0) but state 3-after-2 sets the flag as well, so it was probably OK; new sequence is (1,3)(2,3)(2,2)(2,1)(2,0)(3,0), 1 s apart. Slave msg 8 -> `0xe9edc0` fires the same events with 0 and runs the pawn-list loop (safe when no pawn exists).
7. Strings of AddPlayer: first str (+0xd) = player name -> player table name; second str (+0x2d) = syndicate name `sname` (FUN 0x10026e80) [M]. 0x4e22 `vec<u8>` = face data; used only when length >= 0x38 [H].
