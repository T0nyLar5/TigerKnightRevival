## Battle step 3 (spawn / battle start; Win32 SyncClient.dll + Sync.dll, 2026-11-05)
NOTE for Ghidra: `tools\ghidra_projects\_in\` is keyed by file name only, so Win32 and Win64 `SyncClient.dll` collide; the project now holds the **Win32** SyncClient.dll (addresses 0x100...) and Win32 Sync.dll.

**Key finding**: the client does NOT spawn units from MsgCmd* top-level messages. The frame payload (MsgFramework body string) is a list of `len|type|body` messages handled by the *slave simulation in Sync.dll* (`SyncSlave` vtable 0x1012a154; frame sink 0x10033bf0 -> deserialize 0x100344e0 -> per-message dispatch 0x100348c0 + creation/control dispatch 0x10034630). Our earlier start sequence (0x4e91/0x4e92/0x4e96) went to a different path, so no unit ever existed: no hero, nothing for the timer to tick.
Slave message ids: 1-5 create units (AddPlayer/AddPerson/AddCreature/AddBullet...), 6-0x10 battle control, 6..0x1a0 per-unit messages whose first field is the unit uid (unknown uid -> log "can not find uid"; a unit whose agentId is -1 gets its messages filtered). Top-level types 0x4e20 (CmdSync), 0x4e22, 0x4e23, 0x4e52, 0x4e80, 0x4ecc have special handlers in SyncClient (b41c0); everything else is re-serialized into slave vtable+0x5c.

**Primitive encodings (Sync.dll)** [H]: uvar = LEB128 (0x10003630), svar = zigzag LEB128 (0x1000a3d0), float = **IEEE half (2 bytes)** via 65536-entry table at 0x100e8648 (0x10003870), bool = 1 byte (0x10001260), header = u16 len, u16 type.
**Message 1 (AddPlayer?)** [reader 0x1003bb80, H layout, M meaning]: `uid uvar | kind svar | f0c uvar | f10 uvar | 7 x f16 | bool`. Dispatcher passes uid=+4, kind=+8, pos=floats 0-2, dir=floats 3-5, float6=+0x2c; f10 is stored as the unit's +0x70 and the player-table entry +0x248; f0c != 0 triggers an extra attach (0x10033f40); bool==0 sets player-table flag +0x2d0; uid is registered as the player's unit id (+0x8c / +0x24c). Messages 2,3 share one reader (uid,kind,f0c,f10,6 x f16,uvar,f16,uvar) [0x1003be20]; message 4 = uid,kind,6 x f16 [0x1003c280]; all NOT sent yet.
**Message 8** (header only) [0x10036f60]: sets slave running flag (+0x2c)=1 and calls the UE3-side callback (+0x174 vtable+0x14); guessed to be MsgBattleStart. Siblings: 9 (flag=0, callback +0x18), 0xa (+0x20, 1 byte), 0xc/0xd/0xe/0xf/0x10 other callbacks (pause/end/...). Message 7 -> callback +4 (maybe prepare/init); body unknown.
**Unit creation also needs a UE3-side player event registered for the uid** (0x10038440 does `IPlayerEvent` lookup by uid, else falls back to a null event) so a hero may still not render without more messages.

**Implemented** (`server/battle_proto.py`, `server/battle_server.py`, selftest passes): in the first frames after connect, frame payloads carry `AddPlayer(uid=playerId, kind 0, pos 0,0,0, dir 1,0,0)` then `BattleStart`; then the old UserLoadingFinish/LoadingComplete/CountDown sequence. `--no-spawn` disables the new part. Confidence: layout/encoding high; that this exact AddPlayer parameter set (kind=0 hero type, uid=10001) spawns a visible hero: low-medium; that message 8 starts the clock: low-medium.
**Next test: look in the log for** (a) any client message other than ReqSelfPing (a Req* after our frames shows the master is expected to answer); (b) whether the character appears / countdown moves. If a hero appears but is wrong or stuck, vary kind/f0c/f10 (hero id from the lobby `heroType`) in `msg_add_player`. If nothing, remaining hypotheses: (1) a 0x4e20 CmdSync snapshot is needed first (slave vtable+0x50 in SyncClient, sets synced flag [+0x98]); (2) message 7 (init) must precede AddPlayer; (3) kind must be a real hero/unit id from the (still encrypted) config tables; (4) AddPerson(2)/AddCreature(3) troops must follow; (5) MsgCmdAddPlayer (0x4e..) via top-level path is the UE3-side registration for the uid.
